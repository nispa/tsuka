01 Modello Architetturale a 3 Livelli

L'architettura di TSUKA è strutturata in 3 layer disaccoppiati per garantire che l'interfaccia CLI, il motore agentico ed il registry dei tool siano totalmente indipendenti:

LayerComponenti PrincipaliResponsabilità
CLI Layer src/cli/index.ts, StreamRenderer, ui.ts, initCmd.ts REPL interattiva, rendering token live, gestione dello stream ``, comando tsuka init.
Core Layer Agent, LLMProvider, Blackboard, EffortControl, RunController Ciclo ReAct, gestione del contesto, misurazione dei token, lavagna di run e retry loops.
Tool & Safety Layer ToolRegistry, PermissionManager, auditCode, impl/*.ts Discovery dinamica dei tool, autorizzazione SAFE/RESTRICTED/DANGEROUS, workspace jail.

02 Ciclo ReAct, Timeout e Context Budget

Il motore agentico Agent.run() implementa il pattern ReAct (Reason + Act) con pruning deterministico:

  • Timer a Orologio Continuo (llmTimeoutMs): Copre l'intera durata della generazione del modello (compreso il ragionamento nei tag ``), evitando che chiamate incantate blocchino il processo.
  • Context Budget Bar: Calibrazione esatta dei token e pruning automatico della history al superamento del 75% della finestra di contesto del modello.

03 Sicurezza, Workspace Jail ed Audit Difensivo

TSUKA adotta una politica di sicurezza a controllo utente User-in-the-loop:

  • Livello SAFE: Scritture nulle, lettura file (read_file, grep_search) e scansione di vulnerabilità difensiva (audit_code).
  • Livello RESTRICTED: Modifiche al filesystem (write_file, edit_file, delete_file) con richiesta di conferma [y/N/sempre].
  • Livello DANGEROUS: Comandi di shell (execute_command) che richiedono **sempre** l'approvazione esplicita manuale dell'utente.
  • Workspace Jail: Isolamento e restrizione di ogni path di I/O entro i confini della cartella di lavoro attiva.

04 Multi-Agente, Blackboard di Run e Parallel Staging

I workflow avanzati /team e /goal gestiscono l'esecuzione sequenziale e parallela con garanzia di isolamento:

  • Blackboard di Run (blackboard.ts): Stato condiviso in-memory di un singolo workflow basato su AsyncLocalStorage, accessibile via post_note e read_notes. Distrutto alla fine del run per non inquinare la memoria persistente.
  • Workspace Paralleli (parallelWorkspace.ts): Ogni ramo di un blocco PARALLELO di /goal opera in una propria directory di staging isolata (workspace/parallel-n/), con fusione e rilevamento automatico dei conflitti al termine.
  • Run Controller (loop.ts): Controllore esecutivo con verifiche oggettive che innesca cicli di correzione guidati dal supervisore.

05 Gestione della Creatività e dello Sforzo di Ragionamento

TSUKA introduce una cascata di configurazione trasparente per il campionamento ed il ragionamento:

  • Campionamento Sintetico (samplingParams): Mappatura tramite preset umani precise, balanced, creative.
  • Reasoning Effort (/effort): Controllo dello sforzo di pensiero dei modelli di ragionamento (none, low, medium, xhigh, auto, ask).

06 Architettura Multi-Skill (Ruoli Modulari)

Un personaggio in TSUKA può supportare un array di ruoli differenti (roles: ["developer", "architect"]) e commutare la propria competenza attiva a caldo durante la sessione tramite il comando slash /skill [nome] o il tool SAFE switch_skill.

07 Evoluzioni Future (Backlog T10.1)

L'evoluzione futura programmata nel backlog (Task T10.1) prevede il Dynamic Model Auto-Routing: l'orchestratore seleziona ed assegna autonomamente il modello LLM più adatto ed economico ad ogni agente del team basandosi sui profili di fingerprinting misurati da /benchmark (models_profile.json).
